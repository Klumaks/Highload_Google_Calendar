## Глава 1. Тема и целевая аудитория

### 1.1 Тема проекта, рыночная ниша и аналоги

**Выбранная тема:** проектирование бэкенда высоконагруженного сервиса для планирования встреч, событий и дел - **«Google Calendar»**.

**Реальные аналоги:** Microsoft Outlook Calendar, Apple iCloud Calendar, Zoho Calendar, Calendly. Наличие независимых глобальных игроков на протяжении последних лет однозначно подтверждает существование устойчивой и крупной рыночной ниши - потребности массового пользователя и корпоративных клиентов в планировании встреч, событий, дел и синхронизации расписаний между различными устройствами.

---

### 1.2 Целевая аудитория: размер и локализация

Целевая аудитория - массовый пользователь мобильных устройств и ПК, использующий сервис для планирования встреч, событий и дел, а также корпоративные клиенты через Google Workspace. Сервис имеет глобальное распространение с выраженной концентрацией в США и развитых рынках.

#### Ключевые метрики аудитории

### 1.3 Функционал MVP

Для проектирования выделены следующие **6 ключевых функций**, покрывающих основной пользовательский путь:

1. **Регистрация и авторизация.** Создание аккаунта, вход в систему и управление сессиями.
2. **Создание и редактирование календарей.** Базовое управление сущностями календарей.
3. **Управление доступом.** Каждый календарь можно сделать общедоступным либо предоставить отдельным людям доступ к нему (просмотр или редактирование) через приглашение по электронной почте.
4. **Уведомления.** Отправка уведомлений о предстоящих событиях по электронной почте.
5. **Управление событиями.** Создание и редактирование событий внутри календарей.
6. **Поиск по событиям.** Полнотекстовый поиск по названию, описанию, участникам и дате события внутри всех календарей пользователя с фильтрацией по дате и ключевым словам.

#### Ключевые продуктовые решения

1. **Хранение повторяющихся событий.** Вместо создания тысяч отдельных записей для каждой встречи (например, "планёрка каждый понедельник на год вперёд") в базе данных хранится только одно правило повторения. Конкретные встречи создаются "на лету" при просмотре календаря. Это позволяет экономить огромное количество места и легко редактировать всю серию сразу.

2. **Синхронизация между устройствами.** Когда пользователь открывает календарь на телефоне, приложение не скачивает все события заново. Оно запрашивает только те события, которые изменились с момента последнего открытия. Это экономит мобильный трафик пользователя и снижает нагрузку на серверы.

3. **Гарантированная доставка уведомлений.** Система устроена так, что напоминание о встрече может прийти дважды, но никогда не потеряется. Это важнее, чем избежать дублей, потому что пропустить напоминание о важной встрече - гораздо хуже для пользователя.

## 2. Расчёт нагрузки

### 2.1. Исходные продуктовые метрики

| Показатель | Значение | Основание |
| --- | --- | --- |
| Месячная аудитория (MAU) | **500 млн** | [1], [2] |
| Дневная аудитория (DAU) | **275 млн** | MAU × DAU/MAU ratio 55% [7] |
| Зарегистрированных аккаунтов | 3 млрд | [1], [2] |
| Событий создаётся в месяц | **3,55 млрд** | Расчёт: DAU × 0,43 × 30 [7] |
| Уведомлений доставляется в месяц | **16,8 млрд** | Расчёт: события × фан-аут 7,9 × 0,6 [4], [5], [7] |
| Устройств на пользователя | **3** | Телефон + рабочее устройство + личное устройство |
| Синхронизаций на устройство в день | **64** | Каждые 15 минут в течение 16 часов [6] |
| Коэффициент пика | **4** | Утренний и вечерний пики |

#### Обоснование DAU

DAU не принимается линейно как `MAU × дней / 30`. Используется коэффициент вовлечённости DAU/MAU. Согласно Microsoft Work Trend Index 2026 [7], корпоративные пользователи продуктивных инструментов демонстрируют DAU/MAU ratio в диапазоне 50–70%. Для календаря принимаем **55%** как среднее значение для смешанной аудитории (корпоративные + личные пользователи).

```
DAU = 500 млн × 0,55 = 275 млн
```

#### Обоснование количества событий

Согласно **Microsoft Work Trend Index 2026** [7], корпоративные пользователи проводят **11–15 часов в неделю на встречах**, что соответствует примерно **15–20 встречам в неделю** для активных организаторов (при средней длительности встречи 45–60 минут).

Для расчёта используем **сегментацию как проектное допущение** с обоснованием частот через данные конкурентов:

| Сегмент | Доля | Событий/день | Обоснование частоты | Вклад |
| --- | ---: | ---: | --- | ---: |
| Корпоративные организаторы | 8% | 3,0 | Microsoft Work Trend Index: 15-20 встреч/неделю для активных организаторов ≈ 3 события/день [7] | 0,240 |
| Корпоративные участники | 12% | 0,1 | В основном принимают приглашения, редко создают сами | 0,012 |
| Личные активные | 20% | 0,8 | Типичный паттерн: 5-6 личных событий в неделю | 0,160 |
| Пассивные | 45% | 0,03 | ~1 событие в месяц | 0,0135 |
| Минимальные | 15% | 0,005 | 1-2 события в год | 0,00075 |
| **Итого** | **100%** | — | — | **0,426 ≈ 0,43** |

```
Событий в месяц = 275 млн × 0,43 × 30 ≈ 3,55 млрд
```

**Примечание:** Доли сегментов являются проектными допущениями, основанными на типичных паттернах использования календарей. Частоты создания событий для корпоративных организаторов подтверждены данными Microsoft Work Trend Index [7]. В реальном проекте доли сегментов определяются через A/B-тестирование и анализ поведения пользователей после запуска.

#### Обоснование количества уведомлений

Уведомления считаются как фан-аут событий на участников. 

Согласно **Microsoft Work Trend Index 2026** [7], средняя корпоративная встреча включает **5–7 участников**. Лимит гостей на событие в Google Calendar составляет 200 человек [4], а стандарт iCalendar `ATTENDEE` описывает модель участников [5]. 

Для расчёта используем сегментацию по типам событий:

| Тип события | Доля | Участников | Обоснование | Вклад |
| --- | ---: | ---: | --- | ---: |
| Личная встреча | 50% | 1,5 | Встречи 1-на-1, личные дела | 0,75 |
| Рабочая встреча | 35% | 5 | Microsoft WTI: средняя встреча 5-7 участников [7] | 1,75 |
| Крупное мероприятие | 12% | 20 | Командные встречи, тренинги | 2,40 |
| Массовое | 3% | 100 | All-hands, вебинары (лимит 200 [4]) | 3,00 |
| **Итого** | **100%** | — | Средневзвешенное количество участников | **7,9** |

Принимаем, что **60% событий генерируют уведомления** (остальные 40% - личные заметки и события без гостей, которые не требуют фан-аута).

```
Уведомлений в месяц = 3,55 млрд × 7,9 × 0,6 ≈ 16,8 млрд
```

#### Обоснование частоты синхронизации

Согласно официальной документации Android WorkManager [6], периодическая работа имеет минимальный интервал 15 минут:

> "Periodic work has a minimum interval of 15 minutes."

Это ограничение введено для сохранения заряда батареи мобильных устройств. Принимаем интервал синхронизации **каждые 15 минут** в течение 16 часов активного использования устройства:

```
Синхронизаций на устройство в день = 16 часов × 4 = 64
Синхронизаций на пользователя в день = 3 × 64 = 192
```

Для объёмов хранения используются двоичные приставки: 1 КиБ = 1024 Б, 1 МиБ = 1024² Б, 1 ГиБ = 1024³ Б, 1 ТиБ = 1024⁴ Б. Для сетевого трафика используются десятичные приставки: 1 Гбит/с = 10⁹ бит/с.

## 3. Глобальная балансировка нагрузки

### 3.1 Функциональное разбиение по поддоменам

Для гибкого управления трафиком, изоляции отказов и применения разных таймаутов сервис разделён на функциональные поддомены в рамках родительского домена `calendar.google.com`:

| Поддомен | Назначение | Тип трафика | Стратегия балансировки |
| --- | --- | --- | --- |
| `api.calendar.google.com` | Основной API (создание/редактирование/удаление событий) | TCP/HTTPS, короткие запросы | GeoDNS + EDNS (L7) |
| `sync.calendar.google.com` | Инкрементальная синхронизация (long-polling/WebSocket) | TCP, долгоживущие соединения | GeoDNS + EDNS (L7) |
| `search.calendar.google.com` | Полнотекстовый поиск по событиям | TCP/HTTPS, тяжёлые запросы | GeoDNS + EDNS (L7) |

**Разделение на поддомены даёт:**
1. Разные таймауты (`sync` — 15–30 мин, `api` — 5–30 сек, `search` — 60–120 сек);
2. Изоляцию отказов (падение поиска не убивает синхронизацию);
3. Независимое масштабирование каждого компонента.

---

### 3.2 Обоснование расположения ДЦ и их ролей

Дата-центры располагаются в регионах с наибольшей концентрацией пользователей (на основе данных из раздела 1.2). Архитектура хранения данных использует модель **единого глобального мастера**.

| ДЦ | Регион | Доля MAU | Роль | Обоснование |
| --- | --- | ---: | --- | --- |
| **Франкфурт (Германия)** | Европа | 26,7% | **Глобальный мастер** (единственная точка записи) | Соответствие GDPR, географическая центральность |
| Вирджиния (США) | Сев. Америка | 38,4% | Реплика для чтения | Крупнейший рынок, минимальный RTT |
| Мумбаи (Индия) | АТР | 22,8% | Реплика для чтения | Покрытие азиатской аудитории |
| Сан-Паулу (Бразилия) | Лат. Америка | 12,1% | Реплика для чтения | Покрытие южного полушария |

**Почему Франкфурт выбран глобальным мастером:**
1. **Соответствие GDPR** — данные европейских пользователей (26,7% MAU) обрабатываются внутри ЕС;
2. **Географическая центральность** — относительно равномерная задержка до остальных регионов;
3. **Единая точка записи** устраняет проблему фан-ина при чтении (не нужно объединять данные из нескольких БД).

### 3.4 Схема DNS балансировки (GeoDNS + EDNS)

Все поддомены балансируются через **GeoDNS** с поддержкой расширения **EDNS-Client-Subnet (ECS, RFC 7871)**.

**Как это работает:**
1. Клиент делает DNS-запрос к резолверу провайдера;
2. Резолвер передаёт запрос авторитетному DNS-серверу, добавляя EDNS-Client-Subnet с реальной подсетью клиента;
3. Авторитетный DNS определяет регион и возвращает IP ближайшего ДЦ;
4. Клиент подключается к этому IP и остаётся привязан к ДЦ на время TTL (30 секунд).

**Решение проблемы «слепоты» GeoDNS:**

Классический GeoDNS видит IP-адрес DNS-резолвера (например, 8.8.8.8), а не конечного клиента, что может привести к неверной маршрутизации (например, европеец через Google DNS попадёт в США — нарушение GDPR).

EDNS-Client-Subnet решает эту проблему: резолвер передаёт реальную подсеть клиента, и авторитетный DNS корректно направляет его в нужный регион.

- **TTL = 30 секунд**: Короткое время жизни записей обеспечивает быстрое переключение трафика при аварии ДЦ (~40 секунд с учётом времени детекции Health Checks).

 Anycast не используется

### 3.6 Механизм регулировки трафика между ДЦ

#### Модель «Единый глобальный мастер»

Архитектура использует **единственную точку записи** во Франкфурте и полные реплики для чтения в остальных ДЦ. Это устраняет проблему фан-ина и упрощает модель консистентности.

#### Обработка аварий (Failover)

**Если падает мастер-ДЦ (Франкфурт):**

1. Health Checks обнаруживают падение (10 сек);
2. GSLB исключает Франкфурт из DNS-выдачи;
3. Чтение: трафик перенаправляется в ближайший живой ДЦ с репликой;
4. Запись: manual failover — одна из реплик (обычно Вирджиния как ближайшая) повышается до мастера;
5. После восстановления: данные синхронизируются обратно во Франкфурт.

## 4. Локальная балансировка нагрузки

### 4.1. Схема балансировки нагрузки

Архитектура локальной балансировки разделена на обработку внешнего (входящего), внутреннего (межсервисного) и специфичного для Мастер-ДЦ (Франкфурт) трафика.

#### 4.1.1. Входящий и межсервисный трафик (Стандартный ДЦ)

| Уровень / Тип | Технология | Алгоритм | Обоснование (из материалов курса) |
| :--- | :--- | :--- | :--- |
| **L4 (Внешний VIP)** | **DPVS** (DPDK) / **NFWARE** | Consistent Hashing (Maglev) | Обход ядра ОС (user-space), защита от SYN-flood, >10 млн PPS. Направляет TCP-потоки на L7-ноды, сохраняя сессии. |
| **L7 (API, Search)** | Nginx Ingress | Weighted Round-Robin (динамический) | **Подход Badoo**: автоматический подбор весов на основе времени отклика бэкендов (Least Response Time). Защита от деградировавших нод. |
| **L7 (Sync)** | Nginx Ingress | **Least Connections** | **Практика Heroku**: для долгоживущих соединений (WebSocket/long-polling) Round-Robin вызывает дисбаланс. Алгоритм направляет запрос на ноду с минимумом открытых сокетов. |
| **Межсервисный** | Sidecar Proxy (Envoy) + IPVS | Least Connections | L7-балансировка локально на клиенте. Обеспечивает Circuit Breaker, retries и mTLS без изменения бизнес-кода. |

#### 4.1.2. Специфика Франкфурта (Глобальный Мастер)

Так как Франкфурт принимает 100% глобальных операций записи (включая проксирование из США, АТР и LATAM), его схема дополняется следующими уровнями:

| Компонент | Технология | Алгоритм | Задача и Обоснование |
| :--- | :--- | :--- | :--- |
| **Internal L7 Ingress** | Nginx / Envoy (mTLS) | Weighted Round-Robin (динамический) | Приём проксированных write-запросов от бэкендов других ДЦ по внутренним backbone-каналам. Обязательная взаимная аутентификация (mTLS). |
| **L4 DB Pooler-HAProxy (TCP)** | HAProxy (TCP) | Least Connections | Долгоживущие соединения, важно количество активных коннектов |
| **L4 DB Pooler-PgBouncer** | PgBouncer | Transaction pooling (режим пулинга) |Короткие write-транзакции, нужна экономия соединений. |



---

### 4.2. Механизмы резервирования и отказоустойчивости

#### 4.2.1. Формулы резервирования

| Компонент | Формула | Режим | Обоснование |
| :--- | :---: | :--- | :--- |
| **L4 LB (Входной VIP)** | **N+1** | Active-Passive (VRRP/keepalived) | 1 активный узел держит VIP, 1 в hot-standby. Перехват VIP при падении за <1 сек. Устраняет SPOF на входе в ДЦ. |
| **L7 LB (Nginx Ingress)** | **N×2** | Active-Active | Stateless. Резерв N×2 позволяет пережить падение половины нод (авария стойки, Rolling Update) без исчерпания лимитов SSL CPS. |
| **L4 DB Pooler (Франкфурт)**| **N+1** | Active-Passive (VRRP) | Резервирование пула соединений. При падении ноды пулера бэкенды из других ДЦ не теряют связь с БД. |
| **Backend (API/Sync Pods)** | **N×2** | Active-Active (K8s HPA) | Запас подов для переживания rolling updates и пиковых burst-нагрузок. |
| **PostgreSQL (Франкфурт)** | **N+2** | 1 Master + 2 Sync Standby | Синхронная репликация внутри ДЦ. RPO=0: транзакция не подтвердится (в т.ч. проксирующему региону), пока не запишется в двух независимых зонах. |

#### 4.2.2. Схема отказоустойчивости и Health Checks

| Механизм | Настройки / Описание | Эффект |
| :--- | :--- | :--- |
| **Health Checks (L4/L7)** | `interval=5s`, `timeout=2s`, `fall=2`, `rise=2` | Нода исключается из пула за 10 сек при сбое. Возвращается после 2 успешных проб. |
| **SSL Session Reuse** | **Session Tickets (RFC 5077)** | Снижение нагрузки на CPU L7 в 4-5 раз. Клиенты повторно используют параметры сессии без полного ECDHE handshake. |
| **Circuit Breaker** | Sidecar Proxy (Envoy) | При деградации БД/поиска прокси возвращает fallback-заглушки, предотвращая каскадный отказ (Graceful Degradation). |
| **Graceful Drain (Sync)** | WebSocket control frame | При выводе Sync-пода из строя L7 отправляет сигнал reconnect, предотвращая шторм переподключений. |

### 4.3. Расчёт количества балансировщиков

Расчёт ведётся по двум главным ограничителям: **SSL Termination (CPS)** и **Пропускная способность (Bandwidth)**. 
*Базовый расчёт выполнен для **Вирджинии** (максимальный клиентский трафик: 6,18 Гбит/с исходящего, ~40 000 CPS).*

#### Ограничитель 1: SSL Termination (CPS)

Согласно бенчмаркам Nginx (2017), одна нода (8-16 vCPU) выдаёт ~15 000 CPS (RSA 2048) или ~35 000 CPS (ECDHE) *без* переиспользования сессий.

| Параметр | Значение | Обоснование / Расчёт |
| :--- | :--- | :--- |
| Пиковый CPS (новые подключения) | 40 000 | Sync + API (Вирджиния) |
| SSL Session Reuse (RFC 5077) | **80%** | Сбор статистики через `tcpdump`: 80% соединений используют Session Tickets. |
| Эффективная нагрузка ("тяжёлые" CPS) | **8 000** | 20% от 40 000 требуют полного ECDHE handshake. |
| Производительность 1 ноды Nginx | 30 000 CPS | С запасом покрывает пик "тяжёлых" CPS. |
| Требуется нод (без резерва) | 1 | `8 000 / 30 000 = 0,26` |
| **Итого (с формулой N×2)** | **4 ноды L7** | Покрытие Rolling Update и аварии стойки. |

#### Ограничитель 2: Пропускная способность сети (Bandwidth)

| Параметр | Значение | Обоснование / Расчёт |
| :--- | :--- | :--- |
| Пиковый исходящий трафик | 6,18 Гбит/с | Вирджиния (38,4% глобального трафика) |
| Сетевой интерфейс 1 ноды | 2×10 Gbps | Стандарт для DPVS/NFWARE и Nginx. |
| Пропускная способность 1 ноды | >15 Гбит/с | С учётом оверхеда TCP-стека. |
| Требуется нод (без резерва) | 1 | `6,18 / 15 = 0,41` |
| **Итого (с формулой N×2)** | **4 ноды L7** | Гарантия отсутствия дропов при падении одной ноды. |

*Примечание: Для L4 (DPVS/NFWARE) требуется 2 ноды (N+1), так как один узел способен прокачать >20 Гбит/с и >10 млн PPS.*

Количество L7-нод масштабируется пропорционально нагрузке региона. Франкфурт дополнительно получает L4 DB Pooler из-за роли Глобального Мастера.

| **Мумбаи** | Реплика (Чтение) | 2 | 3 | - | **5** |
